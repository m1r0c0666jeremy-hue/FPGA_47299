## 代码审查发现

### 1. 打包复位修复未进入综合（高优先级）

`td_project/criticalwork.al:158` 选择 `user_source/hdl_source/isp/data96_128/data96_128.v`，该文件的 `data_96bit_to_128bit` 模块仍未使用复位；`reports/criticalwork_build.log:395` 也显示实际从该路径展开。

队友修的是 `user_source/hdl_source/data_96bit_to_128bit.v`，这个文件没有加入工程列表。对相同复位测试，实际文件FAIL、未接入的修复文件PASS。应在后续修复时选择唯一有效实现，更新工程/仿真依赖并重新编译，不能把两份同名模块同时加入。

### 2. FIFO空标志不能代替输出数据有效标志（高优先级）

`video_out.v:177` 使用 `S_video_rd_en_1d && !S_fifo_emtpy` 决定输出像素。FIFO最后一个128位字被取走时，队列变空，但输出寄存器仍保存该字的有效数据，且后面几个24位像素还要使用它。直接看当前empty会把这些像素抹成黑色。

新增测试预填3个128位字（正好16个RGB888像素），无新的DDR返回，要求输出16个有效像素；仿真中像素10～15共6个被输出为黑色。模型为理想FIFO，只证明外围控制存在此边界问题，未宣称是物理FIFO波形实测。此外空时像素计数仍前进，之后返回数据并无完整的字节相位恢复机制。

后续应按成功读出的数据建立有效状态，按流水延迟对齐到每个像素，并明确欠载时丢整行/整帧或重新同步策略，而非简单延迟empty掩盖问题。

### 3. 满写门控不等于坏帧隔离（中优先级）

`video_in.v:61` 的满写门控有效；`S_fifo_overflow`（定义第40行）在满时置位，但没有被任何输出、读写地址或帧指针选择逻辑使用。丢掉一个128位字之后，后续数据仍写入连续地址，存在错位/旧帧残留风险。

未消费的标志可能被综合优化，不能仅凭RTL里有名字就说可用ChipWatcher观测。应将溢出与整帧有效性、提交读指针及可见诊断相连；该修改本轮未进行。

## 引脚独立核对

已读取原资料中的《新HX1P35A开发板手册-HDL版2604.pdf》，正文页6/13/14/15/20/23（本文件页号与PDF物理页号一致），并查看相关表格渲染图。该手册在 `9_康芯开发板使用手册及实验平台/`。主要映射：

| 项目 | 手册与当前工程 |
|---|---|
| 50MHz时钟 | C4 |
| KEY1复位、KEY2/3输入 | D5、A9/B9 |
| LED1心跳 | D10 |
| 摄像头SCL/SDA/参考/控制 | K3/J3/L3/L2 |
| HDMI D0正/负 | G16/H16 |
| HDMI D1正/负 | F17/E18 |
| HDMI D2正/负 | H14/H13 |
| HDMI时钟正/负 | C17/D18 |

以上也与 `criticalwork_phy.area` 的Detailed IO Report一致。相比此前用HX1P35B标题原理图作对照，这份HX1P35A手册提供了更匹配的依据。它解决了主要文档对照疑问，不替代实际PCB修订号、完整DDR和排线映射留档。手册对FPC的文字"42脚"与历史"40P"称呼不同，不据名称另改排线，实际以连接器图和已验证配套线为准。

远端旧文档中的"修正前也不会损坏器件"是过强结论：当前映射和出图不足以证明所有旧接法、板卡版本均无电气风险。旧bit仍不得自动沿用新版本的确认结果。掉电也不能作为DDR内容确定清零的保证；残影消失现象不能单独证明其根因或完整帧写入已正确。
